# 与 Agent 协作指南 + 最佳实践

这篇文档讲清"你和 AI 做地图"怎么配合最顺，也算共同约定。**两条最重要：先对齐效果再动手，绝不猜；你只管用大白话说需求，配置我来写、我来检查。** 下面直接写清楚，不依赖任何 skill 文件；想弄懂哪个概念，直接问 AI 就能得到回答。

> 一张地图 = 格子配置 + 全局配置（字段/区域/计费/昼夜/税）+ 行为（事件效果）。你不需要背结构，AI 会转成人话给你听。

## 三种开工方式

- **从全貌开始**：先讲"我要一张 XX 主题的地图、几块区域、特色是…"，AI 先把整体布局和分区理清，写成设计说明给你确认，再逐格落。
- **接手别人的图**：AI 先读一遍现成地图，写一份现状说明（有哪些格、各区域、彩蛋、已知取舍），你点头后再谈改动。
- **逐格增改**：直接说 `加个地产格，价格100，租金10/20/30/40，最高3级`。想加彩蛋就 `加个彩蛋奖励：…`，想配昼夜就 `这个区夜晚繁荣会降`。

> 无论哪种方式，改动都会同步更新那张图目录下的注释文档。

## 一、协作的原则共识

1. **自然语言为主**：正常流程只说你要什么，不手写 JSON。
2. **先对齐、后生成**：描述有歧义时，AI 先用大白话复述并追问缺失项（如最高等级、升级费用），确认"无歧义"才动手。
3. **校验把关**：任何改动入库前都先自查；对不上就明确指出是哪一处、怎么改。
4. **不懂就问**：直接问 AI 任何概念，它能解释。

## 二、Agent 的标准对话脚本（示例）

```
协作者：我要一个 property 格子，id=5，价格 100，租金 10/20/30/40，可升 3 级。
Agent  ：收到。确认一个点：升级费用如何递增？（缺省我按 50/100/150）
协作者：50/100/150。
Agent  ：已生成，校验通过。要提交到地图仓库吗？
协作者：提交。
Agent  ：已提交。commit: abc123
```

### 什么时候 Agent 应主动追问
- 提到了"等级/递增"但没说数量或费用。
- 提到了要"分红/扣款"但没说触发条件。
- 提到了 UCT 字段但没说作用域（player/region）或正负方向。

## 三、正负号速记（最容易错的地方）

| 意图 | 写法 |
|---|---|
| 玩家支付 / 被扣 | `money: -X` |
| 玩家获得 / 被加 | `money: +X` |
| 加信用 | `credit: +X` |
| 区域繁荣升 | `region: { "pros": +X }` |

> 代码统一 `+=`；正负号写在数据里。**别写错方向**，校验能识别但不代表语义对——生成后请让 Agent 用一档句子复述效果。

## 四、内容构思协助（想不到就把想法丢给 AI）

地图效果没有标准答案。**想不出/不确定怎么设计时，直接让 AI 帮你构思**，它给方案、你来挑或调整，全程用大白话：

- "帮我构思一个高风险高回报的 investment 格子。"
- "设计一个和昼夜相关的 event 效果，奖励/惩罚要平衡。"
- "这个区夜晚繁荣会降，帮我配几个能抬繁荣的格子。"
- "彩蛋格奖励给多少数值合适？给个合理的量级。"

> 这让 UCT 字段、behavior 效果的自由设计落到实处——你不需要先想好完全方案，说清**主题/感受/大致尺度**，AI 会补全数值平衡、触发方式等细节供你选择，确认后才写入配置。

## 五、schema 变更会造成存量地图失效

主仓库的 UCT/行为 schema 可能演化。规则：
- 合并进主仓库时强制重跑校验。
- 本仓库**不维护 schema 副本**；如遇校验规则变化，以主仓库为唯一事实源。

## 六、与"微信贴 JSON"回退的关系

- **首选**：Agent 对话产出 + 入库。
- **回退**：直接贴 JSON 给开发者，由开发者侧校验入库。回退时不要求完整 schema，但开发者侧会补校验并回写修正。

## 七、给人类维护者的最佳实践

- **一图一目录**：一张图的全部内容放进 `maps/<图名>/` 这一个目录（格子配置、全局配置、行为子目录、注释文档），方便维护多张图。
- **注释文档**：每张图目录下有 `NOTES.md`，用自然语言说明各项配置；**改任何配置必须同步更新它**。全貌构思/接手他图时沉淀的《设计说明》《现状说明》也放同目录，方便后来者接手。
- 任何字段（id/命名/字段全集）都要与对应 `map-meta.json` 一致，别在格子里引入 `map-meta` 未声明的字段。

## 八、需要遵守的纪律（防技术债）

- 不新增以 `_` 开头的 hack 字段；不通过注释来"软开关"。
- 不复制主仓库 schema 到本仓库，避免漂移。
- 所有校验失败都走"报错->定位->修正"，不使用静默 fallback 掩盖配置缺陷。
