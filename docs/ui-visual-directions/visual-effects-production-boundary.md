# 内测版视效制作需求边界

> 依据：Issue #3「beta（内测版）制作边界」及其评论、当前代码与现有 UI 交接文档。
> 目标：在不偏离内测版“够玩、有趣、好上手”的前提下，补足基础视效框架和一个可感知的分享/首屏演示点。
> 状态：制作边界，不等同于完整视效技术方案。

## 一页结论

本阶段只做轻量、可关闭、服务于状态反馈的视效：

1. 接通现有视效钩子，形成最小可扩展骨架。
2. 完成棋子基础移动动画，并保持逻辑位置与显示位置分离。
3. 提供一个视效总开关，至少支持“开启 / 关闭”两档。
4. 选择一个低成本演示点承担首屏或分享观感，优先选择“地图 + 棋子移动”或“成就达成瞬间”。
5. 保留加载、成功、失败、禁用、断线和减少动态等状态反馈。

本阶段不做整套粒子、纹理、转场、资源注册和高级特效系统，不做会改变玩法规则的表现机制。

## 1. 约束来源与当前事实

### 1.1 产品边界

Issue #3 明确要求：

- 地图规模较大，重点是够玩、有趣、好上手，不要求精调平衡。
- 需要一些简单视效钩子，至少一个能够承载首屏或分享的演示点，观感不能廉价。
- 需要组队、聊天、持久化和账号等内测闭环能力。
- 暂不做过分精细的 UI/VE，但“框架要打”。
- 暂不做复杂地图机制、道具、天赋和 i18n 精翻；当前先做好中文。

评论进一步将视效范围收敛为：基础移动动画、逻辑/显示位置分离和一个视效开关；粒子、纹理、复杂转场、资源注册表及重型 `EffectRuntime` 延后。

### 1.2 当前运行时事实

- 客户端真实可见的地图层是 `InteractiveMapSurface` 生成的 SVG；不能把隐藏的 Canvas 重新设为唯一渲染层。
- `GamePage` 当前创建 `NoOpEffectHooks`，视效接口存在但生产实现尚未接入。
- `MovementSystem` 已有基于 `playerDisplayX/playerDisplayY` 的单步插值逻辑，单步时长当前为 280ms；服务端位置仍由 `GameStore` 的权威投影驱动。
- `GameEffects.ts` 已定义骰子、移动、数值、格子、状态和通知视效钩子，并提供 CSS 过渡实现的部分骨架。
- UI 通过 `GameStore`、`GameViewModel` 和现有事件入口消费状态；视效不得直接连接 Socket、服务端对象或旧模块级业务状态。
- 现有设计系统使用 `DesignAdapter`、`ThemeConfig` 及 CSS 变量；颜色、尺寸、间距、阴影、圆角和动画参数不得在渲染层随意硬编码。
- 全局样式已有 `prefers-reduced-motion: reduce` 处理，新增动态必须与其兼容。

## 2. 本阶段必须交付

### 2.1 最小视效骨架

骨架的职责是统一视效接入点，而不是提前实现完整效果引擎。

必须具备：

- 一个明确的视效能力入口，能够由 `GamePage` 或其下游渲染层注入。
- 一个默认安全实现：视效关闭或未实现时，玩法和状态渲染仍正常工作。
- 一个全局视效开关，视效关闭后不应阻止掷骰、移动、路径选择、购买、组队、聊天和其他既有操作。
- 开关状态在页面生命周期内稳定，不得为每次状态刷新重复创建效果实例。
- 视效触发只能来自已有状态变化或明确的 UI 回调，不新增绕过 `SocketEventHandler` 的事件监听。

不要求：

- 七组件或多层级的通用 `EffectRuntime`。
- 独立资源注册表、预加载器、纹理缓存、粒子调度器。
- 为未来所有效果预留完整参数模型。

### 2.2 基础移动动画

移动动画是本阶段最低限度的“观感不廉价”要求，也是首选演示点。

必须实现：

- 棋子从上一格连续移动到下一格，而不是瞬移。
- 多步移动逐格播放；每步完成后再进入下一步。
- 路径选择时，先保持等待态，展示可选路径；选定后再继续移动。
- 传送等非相邻移动不得伪装成普通逐格移动；至少提供清晰的状态切换或短暂过渡。
- 逻辑位置继续使用服务端权威状态；显示位置只用于动画插值，不能反向写入玩法状态。
- 动画完成后，棋子、摄像机、底部行动组和格子信息展示回到同一份最新 Store 快照。
- 动画期间重复掷骰、重复操作和重复启动同一段移动必须受到现有业务状态约束，不得因视效产生额外请求。
- 服务端事件延迟、断线重连或动画中收到新快照时，必须能够停止、追赶或重置显示动画，不得卡死在半格位置。

建议的默认表现：

- 使用克制的缓入缓出插值。
- 单步时长沿用当前 280ms 基线，除非验证表明大地图或移动密度需要调整。
- 不使用镜头大幅摇晃、强烈缩放、全屏闪烁或持续粒子。
- 地图和棋子保持清晰优先，动画不能遮挡路径、格子名称、行动按钮和聊天区域。

### 2.3 一个首屏 / 分享演示点

本阶段只选择一个主演示点，不并行制作多个大型展示系统。

优先级：

1. 地图与棋子移动：能直接展示核心玩法、多人位置和地图规模。
2. 成就达成瞬间：仅在轻量成就实际接入后采用，不能为了视效提前虚构成就系统。
3. 组队画面：作为已有组队能力的状态强调，不扩展为独立宣传动画。

演示点必须满足：

- 能在本地或部署环境通过正常游戏流程触发。
- 不依赖开发者手动修改 Store、伪造服务端事件或专用隐藏入口。
- 3 秒内能看懂发生了什么，不需要解释复杂规则。
- 在视效关闭时仍能通过文本、颜色、状态或布局变化理解结果。
- 可通过截图或短录屏展示，不出现明显半成品、空白区域、错位棋子或廉价默认效果。

## 3. 允许制作的效果范围

以下内容可以作为本阶段的实现范围，但必须服从“轻量、状态反馈优先、可关闭”：

### 3.1 页面级

- Start、Login、Loading、Game、Bankruptcy 页面之间的基础淡入淡出。
- Loading 的进度或连接状态变化。
- 破产进入和重开状态的清晰强调。
- 昼夜切换的低强度颜色或背景变化。

### 3.2 棋盘与棋子

- 棋子逐格移动。
- 当前玩家或当前行动目标的轻量选中态。
- 路径选择候选格的边框、线条或对比度强调。
- 传送前后的位置状态提示。
- 其他玩家位置更新时的非抢焦点变化。

### 3.3 操作反馈

- 骰子开始滚动、结算和冷却状态。
- 购买地产、升级、投资、修缮等成功后的短暂确认。
- 金钱、信用、环境值、繁荣度变化的轻量数值反馈。
- 通知的出现和消失。
- 错误、禁用、无权限、无连接状态的清晰反馈。

这些效果的最终显示仍应由服务端事件和客户端权威投影驱动；视效只表现状态，不产生状态。

## 4. 明确排除项

以下内容不进入本阶段制作、验收或视效框架设计：

- 整页粒子系统、持续飘散粒子、天气粒子和大规模背景动效。
- 纹理资源系统、材质系统、图像资源回退和复杂资源加载策略。
- 建筑剪影转场、圆形遮罩、复杂镜头转场和全屏场景切换。
- 七组件或更大范围的通用效果运行时。
- 独立资源注册表、资源版本管理、预加载/缓存基础设施。
- 音频系统、音效库和音乐同步；除非另行提出并确认边界。
- 高精度角色、建筑、地图插画、3D 模型或复杂动画资产。
- 为视觉表现新增复杂地图机制、道具、天赋、复杂成就或新的经济规则。
- 以视效为理由修改 Socket 协议、服务端结算、玩家位置权威、所有权、投资分成或破产规则。
- 为了演示点增加专用作弊入口、假数据入口或绕过正常流程的开发按钮。
- i18n 精翻；用户可见文案继续复用现有中文优先的 i18n 资源结构。
- 视效设置面板的多级参数、逐类开关、质量档位和高级性能调节。

## 5. 技术接入边界

### 5.1 数据与调用链

视效调用链应保持以下方向：

```text
server.* 事件
  -> SocketEventHandler
  -> GameStore
  -> GameViewModel / GamePage 编排
  -> 地图、HUD、视效表现
```

要求：

- 不在 `GameHudShell`、`InteractiveMapSurface` 或其他 UI 组件内直接注册 Socket 监听。
- 不从组件直接读取或写入 `currentPlayer`、`currentMoney`、`ownedProperties` 等旧模块级状态。
- 不把 ACK 当作最终业务状态；成功视效应在权威事件或权威快照确认后触发。
- 不把动画显示坐标写回服务端位置或经济状态。
- 页面清理时必须清理动画帧、定时器、事件监听和视效实例，避免重复触发或跨页面残留。

### 5.2 样式与主题

- 复用 `DesignAdapter`、`ThemeConfig` 和既有 CSS 变量。
- 新增的颜色、持续时间、位移幅度、边框、阴影和其他视觉参数应进入现有主题/样式数据层；渲染层只负责逻辑和应用。
- 四种地域主题只做同一效果的参数映射，不为每个区域建立独立效果系统。
- 动态效果不能削弱文本、路径、棋子和按钮的可辨识度。
- 必须兼容 `prefers-reduced-motion`；关闭动态后保留必要的状态变化和结果提示。

### 5.3 性能与兼容

- 优先使用现有 SVG、DOM、CSS transition/animation 和已有插值逻辑。
- 不新增外部视效库，除非先证明现有能力无法满足并单独确认依赖引入。
- 不把 Canvas 重新设为唯一可见渲染层。
- 不使用依赖单一操作系统的路径、资源或命令。
- 大地图下不能因每帧重建整张地图而造成明显卡顿；移动动画应尽量只更新棋子显示位置或最小必要节点。

## 6. 制作顺序

1. 确认 `GamePage`、`GameStore`、`GameViewModel`、`MovementSystem` 和现有 `GameEffects` 的调用关系。
2. 补齐最小视效入口与开启/关闭能力，先确保关闭状态行为完全不变。
3. 接通棋子移动动画，验证单步、多步、分叉选择、传送、断线/重连和页面清理。
4. 接入一个首屏/分享演示点，优先使用地图与棋子移动，不新增玩法数据。
5. 补齐成功、失败、禁用、加载、断线和减少动态状态。
6. 在不改变数据契约的前提下进行 CSS 和主题调校。
7. 通过验收后再根据内测反馈决定是否增加其他轻量钩子；不得预先扩展为完整特效平台。

## 7. 验收标准

### 功能验收

- [ ] 登录后进入游戏，默认视效开关状态明确。
- [ ] 关闭视效后可以正常完成一局核心循环：掷骰、移动、路径选择、落点处理和下一次操作。
- [ ] 开启视效后棋子逐格移动，不出现瞬移、重复移动、卡半格或移动后位置错误。
- [ ] 多玩家同时在线时，当前玩家和其他玩家的位置显示不会互相覆盖或错位到错误格子。
- [ ] 传送、断线重连、服务端快照追赶和页面离开不会留下运行中的动画或错误位置。
- [ ] 至少一个演示点可通过正常流程触发，并适合截图或短录屏。
- [ ] 成功、失败、禁用、加载、断线、破产和减少动态状态均有可理解反馈。

### 架构验收

- [ ] 视效实现从真实页面入口挂载，不是只存在于孤立文件。
- [ ] 视效组件不直接连接 Socket，不绕过 `SocketEventHandler`。
- [ ] 逻辑位置、服务端权威状态和显示插值位置职责清晰。
- [ ] 页面销毁后无残留 listener、timer、animation frame 或重复注册。
- [ ] 没有新增第二份玩家位置、所有权、经济数值或格子状态。
- [ ] 主题参数和现有设计令牌链保持一致。

### 视觉验收

- [ ] 首屏或演示点在不依赖解释的情况下能表达“这是一个可玩的多人地图游戏”。
- [ ] 视觉重点服务于状态反馈，不被粒子、光晕、过渡或装饰抢占。
- [ ] 不出现廉价默认占位效果、明显错位、闪烁、文字遮挡或不可操作按钮。
- [ ] 视效关闭后仍可理解核心状态和结果。
- [ ] 四种地域主题下，效果具有一致的功能语义和合理的调性适配。

## 8. 验证要求

客户端相关改动至少执行：

```bash
pnpm exec tsc -p packages/client/tsconfig.json --noEmit
pnpm --dir packages/client exec jest tests --runInBand
pnpm --dir packages/client run lint
pnpm --dir packages/client run build
git diff --check
```

涉及共享类型、Socket 契约或服务端行为时，追加：

```bash
pnpm --dir packages/shared exec jest tests --runInBand
pnpm --dir packages/server exec jest tests/handlers tests/transport --runInBand
pnpm --dir packages/server exec tsc -p tsconfig.json --noEmit
```

需要人工重点检查：

- 动画中收到服务端新快照时的追赶与重置策略。
- 多步移动结束时 `currentPlayerPosition`、`playerDisplayX/Y`、摄像机目标和地图棋子是否最终一致。
- 视效关闭、`prefers-reduced-motion` 和页面销毁三条路径是否都能清理动态资源。

## 9. 后置候选

只有在内测反馈证明基础移动和一个演示点不足时，才重新评估：

- 更多状态反馈钩子。
- 更丰富但仍短促的区域/昼夜切换。
- 轻量成就达成提示。
- 榜单或组队状态的分享展示。
- 资源化的少量视觉参数。

粒子、纹理、复杂转场、资源注册表、完整效果运行时和高级设置仍属于 demo 之后的候选，不因本文件而自动进入当前制作范围。
