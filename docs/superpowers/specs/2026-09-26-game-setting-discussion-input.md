# 游戏设定讨论 · 输入材料

> **摘要**：本文是交给**另一个 AI 会话**讨论"游戏设定"的输入包，不是运行时规格。核心结论有四条：①设定分三层——**游戏设定（跨地图不变量 / 品牌锚点）> 玩法模式（从当前配置能力抽象出的框架）> 地图实例（`map.json` + `map-meta.json` + `behaviors`）**；②设定层只负责"跨任意地图都不变的东西"，具体机制一律下沉到地图实例；③当前配置里偏棋盘的**内部词汇对玩家可隐藏、可改名**，其本身不承载行为语义；④**不存在需要进入代码的 `gameMode`**，同一时刻服务器只运行一张地图，`gameMode` 至多是对"已能实现的游戏类型"的表述，是配置能力的抽象而非运行时字段。
>
> 讨论前请先读文末"需要附加的文档"，尤其是 `PLAYER.md`（机制严格表述）与 `CONTENT_CREATOR.md`（UGC 可拓展性严格表述）。

---

## 一、这份材料要解决什么

**目标**：为"游戏设定"层建立一份跨地图稳定、可长期维护的定义，使游戏在**不同地图更迭**中维持一致的品牌形象。

**边界**：
- 本文不定义任何新字段、新代码、新机制，只做**概念分层与边界澄清**。
- 设定层**不得**把具体数值、具体格子类型、具体行为写死——那些属于地图实例。
- 讨论产出应当是"设定层文档"，而不是又一版地图配置。

**一句话判断标准**：一条规则如果**换了地图就变了**，它就不属于游戏设定；如果**换任何地图都成立**，才可能是游戏设定的候选。

## 二、三层层级划分

| 层 | 定义 | 变更频率 | 归属 | 载体 |
|---|---|---|---|---|
| 游戏设定 | 跨地图不变量、品牌锚点、呈现契约 | 极低（品牌级） | 产品 / 设定 | 设定文档（待产出） |
| 玩法模式 | 从当前配置能力抽象出的"一类玩法"的框架表述 | 低 | 设计 | 文档表述，**不入代码**（见 §五） |
| 地图实例 | 一张具体地图的全部数据 | 高（每次换图） | 地图作者 / 协作者 | `map.json`、`map-meta.json`、`behaviors/*.json`、`achievements.json` |

### 各层"装什么、不装什么"

**游戏设定（最上层）**
- 装：品牌调性、核心体验承诺、跨地图一致的呈现契约（视觉/文案/反馈的底线）、玩家身份的连续感、跨地图通用的行为准则（如"服务端权威""无回合、随时进出、破产再来"这类体验承诺）。
- 不装：任何具体格子类型、具体数值字段、具体区域、具体地图 id。

**玩法模式（中间层，仅表述）**
- 装：对"当前配置能力能凑出哪几类玩法"的描述，例如偏棋盘的经营对抗、偏叙事的探索推进——**用来说明能力边界，而不是定义运行时分发**。
- 不装：运行时代码里的枚举、分支、数据库字段。原因见 §五。

**地图实例（最下层）**
- 装：格子、区域、数值字段（UCT）、行为脚本、投资监听器、税收、昼夜、骰子、榜单、成就。
- 已具备的抽象能力（证据见 `map-meta.json` 与 `behaviors/`）：数值字段可自由声明（player/region 作用域）、字段可稀疏、行为可自定义效果（`value`/`ownership`/`position` 三类 op）、事件可由"落点/持股人破产"等域事件触发。**这意味着地图作者可以把同一个引擎抽象成非传统大富翁的机制**，只要仍落在"沿有向边移动 + 落点结算 + UCT 数值"这套骨架上。

## 三、品牌锚定与呈现契约

设定层存在的意义是**让"大富翁.io"这个品牌在地图更迭中不散架**。建议把设定层拆成两半：

1. **品牌锚点（不可变）**：名称/调性/核心体验承诺/跨地图一致的基础反馈语言（如破产、入狱、到账的提示语风格）。
2. **呈现契约（可扩展但不漂移）**：规定"无论哪张地图，哪些东西必须保持一致的语义与呈现底线"，而不规定具体皮肤。

呈现契约的候选条款（供讨论，非定稿）：
- 玩家的每一次数值变化都必须以**服务端绝对值**为准并被一致地呈现（当前已如此，见 `PLAYER.md` §十）；
- 任何地图切换/区域切换都**不得让 HUD 与棋盘观感割裂**（这是此前主题切换讨论的根因，见 §六外部参考）；
- 地图可以换皮，但**交互骨架**（掷骰、岔路选择、落点结算、行动入口）保持稳定；
- 文案基调一致；具体文本由地图作者掌控，设定层只给基调不给逐字稿。

> 待另一会话讨论：呈现契约应当多细？太细会限制地图作者的创造力，太粗则品牌无法锚定。

## 四、字段语义的最小契约（设定层与 UI 的桥）

当前 `valueFieldDefinitions` 只有 `{ id, name, scope, min, max }`，**缺少语义类型**。设定层需要给"一个数值字段在体验上属于哪一类"一个最小契约，否则 UI 无法跨地图通用地呈现它。

建议引入（仅表述层，是否入代码待定）三类语义：
- `resource`：可积累、可被消耗、用于交易（如 money）。
- `state`：表征处境、影响可用性（如 credit / 状态值）。
- `progress`：表征进展、有明确目标或上下限（如 region 繁荣度）。

**为什么需要**：HUD 的数值卡片、榜单、成就阈值、颜色与动效都要按语义分类来决定"怎么显示"。若字段无语义类型，换地图后 UI 只能靠 id 猜测，无法给出稳定呈现。

**待确认**：这是否值得进入 `valueFieldDefinitions`（新增可选字段，缺省回退），还是只在设定文档里作为约定。

## 五、内部词汇的中性化（澄清点①）

现状词表中偏棋盘的词汇：
- 8 种固定格子类型：`empty` / `supply` / `event` / `property` / `investment` / `jail` / `transport` / `monument`；
- 机制词：所有权 / 合租 / 租金 / 升级 / 监狱 / 纪念碑 / 税收（`baseTax` + `shareTax`）/ 骰子；
- 行为 op 词：`value` / `ownership` / `position`。

**澄清（用户口径）**：这些词汇**可以对玩家隐藏**，其本身**不承载行为语义**，不影响地图作者把它们抽象成其他类型游戏中的机制。**第二种模式真实出现时**，再考虑换成更中性的表述。

据此的当前执行原则：
- 不在本轮做词表中性化（避免过早抽象、避免改坏现有配置）；
- 设定层可以**预先声明**"玩家可见词汇 vs 内部词汇"的映射意图，但**不落地改名**；
- 一旦出现第二种玩法模式，按届时的需求统一改名，而不是现在猜着改。

## 六、`gameMode` 的定位（澄清点②）

**澄清（用户口径）**：`gameMode` 要**慢一点、抽象一点**。
- 二值 enum（`board` | `narrative`）能解近渴，但**同一时刻服务器只运行一张地图**；
- `gameMode` 只是对"能实现的不同游戏类型"的**表述**，而这些类型都是从当前配置功能**抽象**出来的；
- **不存在需要进入代码的 `gameMode` 定义**。

执行结论：
- 不新增 `gameMode` 字段、不新增代码分支；
- 若讨论中需要引用"模式"，用自然语言描述（如"偏棋盘经营模式""偏叙事探索模式"），**不固化为枚举**；
- 真正的分发依据仍然是"当前加载的是哪张地图"，不是某个模式开关。

## 八、我对设定的看法（观点，非事实）

1. **设定层应当"薄"**。它能锚定的只有调性、承诺、契约；任何具体机制都应能下沉到地图实例。越想把设定写成"玩法规则"，越会与地图作者的创造力打架。
2. **品牌锚点的真正载体是"呈现契约"而非"机制"**。玩家长期记住的是"这类反馈的调性一致"，而不是"有没有土地税"。因此设定层的重心应放在跨地图一致的反馈语言与呈现底线。
3. **抽象能力已经足够支撑非大富翁玩法**（UCT 自由字段 + 行为自定义 + 域事件），所以设定层**不需要**为"未来玩法"预留任何专门结构——只需要不把当前地图的具体概念写进不变量。
4. **中性化与 `gameMode` 都应"按需发生"**，现在不做。过早中性化会把当前地图的可读性换成一个尚未存在的抽象。
5. **风险提示**：设定层若过度抽象（如强行定义 resource/state/progress 之外的类型学），会变成"没有地图能完全满足"的空契约。建议语义类型保持最小（§四），够 UI 用即可。
