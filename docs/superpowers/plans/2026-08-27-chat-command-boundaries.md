# 聊天框指令系统边界

## 概要

本边界文档定义聊天框指令、组队快捷操作、快速反馈和基础敏感词风控的产品与协议范围。当前项目中的所有玩家位于同一个游戏世界，不按房间隔离聊天、组队或玩家可见性。

本阶段目标是让客户端组队功能通过聊天框完成可用闭环，并提供简单、可诊断的内容风控和快速反馈入口。本文只定义边界，不包含实现计划、代码或部署方案。

## 已确认决策

- 指令使用斜杠前缀。
- `/team`、`/region`、`/global` 无参数时切换当前聊天频道；带参数时先切换频道，再将参数作为消息文本发送到新频道。
- 不以 `/` 开头的普通文本发送到当前频道。
- `/invite` 使用唯一用户名，不使用玩家 ID 作为用户输入。
- 不支持 `/kick`，客户端和服务端均不得以聊天指令形式暴露踢人能力。
- `/help` 显示当前支持的指令帮助。
- `/report 内容` 对所有玩家开放，包括游客。
- `/report` 不进入聊天广播；服务端写入反馈记录并写服务端日志。
- 所有玩家共享同一个游戏世界；不引入房间 ID、房间切换或房间级聊天路由。

## 指令集合

| 指令 | 参数 | 结果 | 权限 |
|---|---|---|---|
| `/help` | 无 | 返回指令帮助系统消息 | 已连接玩家 |
| `/team` | 可选文本 | 无参数时切换到队伍频道；带参数时切换后发送文本 | 已连接玩家；无队伍时给出可读提示 |
| `/region` | 可选文本 | 无参数时切换到区域频道；带参数时切换后发送文本 | 已连接玩家；无区域时给出可读提示 |
| `/global` | 可选文本 | 无参数时切换到世界频道；带参数时切换后发送文本 | 已连接玩家 |
| `/invite 用户名` | 唯一用户名 | 创建组队邀请并通知目标玩家 | 已认证且在游戏中的玩家 |
| `/accept` | 无 | 接受一个当前有效的待处理邀请 | 被邀请玩家 |
| `/reject` | 无 | 拒绝一个当前有效的待处理邀请 | 被邀请玩家 |
| `/leave` | 无 | 离开当前队伍 | 已加入队伍的玩家 |
| `/report 内容` | 非空文本 | 保存反馈并返回提交结果 | 所有玩家，包括游客 |

### 未支持指令

以下内容不属于本阶段：

- `/kick`。
- 房间创建、加入、离开和房间聊天。
- 管理员反馈查询、反馈审核、反馈后台或反馈导出命令。
- 私聊、玩家屏蔽、复杂权限矩阵。
- 通过指令直接修改游戏数值、位置、产权或世界状态。

## 普通文本与频道

客户端维护一个当前频道，初始频道沿用现有产品默认值。普通文本不以 `/` 开头时作为聊天内容发送到当前频道。

支持的玩家频道：

- `team`：当前队伍成员可见。
- `region`：当前所在区域的玩家可见。
- `global`：同一游戏世界内所有在线玩家可见。

`system` 仅用于服务端系统提示，不允许玩家通过普通文本或指令发送。

频道指令无参数时只改变客户端当前频道，不发送聊天消息；带参数时先改变当前频道，再将完整参数原文作为纯文本消息发送到新频道。只有消息发送成功后，才向当前客户端确认指令完成；切换成功但发送失败时不得伪装成成功。指令成功、失败或权限不足均通过当前客户端系统消息反馈，不广播给其他玩家。

队伍或区域上下文缺失时不得返回“发送成功”后静默丢失：

- 没有队伍时，`/team` 应提示玩家当前没有可用队伍频道；普通文本不能伪装成队伍消息。
- 没有区域时，`/region` 应提示当前没有可用区域频道；普通文本不能伪装成区域消息。
- `/global` 不依赖队伍或区域。

## 组队邀请边界

### 用户名

- 用户名在账号系统中必须唯一。
- `/invite 用户名` 只按精确用户名匹配，不按模糊匹配、前缀匹配或客户端显示名匹配。
- 找不到用户名时返回统一、可读错误。
- 不因错误提示泄露额外在线玩家信息。
- 用户名解析不得接受空参数或多余未定义参数。

### 竞态与原子性

邀请相关操作必须由服务端作为唯一权威执行，不能依赖客户端预检查结果。以下检查和状态变更必须在同一个同步业务操作中完成：

- 邀请仍为 `pending` 且未过期。
- 响应者确实是邀请目标。
- 邀请者和目标仍存在。
- 邀请者队伍仍存在且未解散。
- 队伍人数仍未达到上限。
- 目标当前队伍状态仍允许加入。
- 接受、拒绝、过期和重复响应之间只能有一个最终结果。

并发响应的约束：

- 同一邀请的两个接受请求最多一个成功。
- 接受与拒绝并发时最多一个生效，另一个返回“邀请已处理”。
- 邀请在接受检查前过期时不得加入队伍。
- 接受因队伍刚满而失败时，不得提前把邀请标记为 `accepted`；邀请应保持可诊断的未处理/失效状态，并返回明确失败结果。
- 队伍合并、离队和邀请接受同时发生时，以服务端串行化后的状态为准，不允许产生重复成员或错误 `teamId`。
- 所有成功或失败结果都必须通过 ack 或系统事件反馈，不允许静默失败。

### 客户端状态

- 客户端只根据服务端权威队伍事件更新队伍成员状态。
- 客户端不得根据“发送邀请成功”自行推断目标已经入队。
- 多个邀请必须各自绑定自己的 `inviteId`，不得通过可覆盖的全局函数处理。
- 邀请接受/拒绝按钮在服务端返回后进入最终状态；重复点击不得重复提交有效操作。

## `/report` 快速反馈

### 可见性与存储

- 所有已连接玩家均可使用，包括游客。
- 反馈只保存到服务端反馈记录，并写入服务端结构化日志。
- 不广播到 `team`、`region` 或 `global` 频道。
- 当前不提供管理员查询、列表、审核、删除、导出或后台入口。
- 反馈记录至少包含：反馈 ID、提交时间、玩家 ID（如有）、游客标识、当前世界标识（如有）、当前格子（如有）和清理后的反馈内容。
- 不记录密码、JWT、认证头、密钥或完整请求对象。

### 输入与限流

- 空内容拒绝。
- 内容长度限制与聊天文本上限保持一致；超限返回可读错误，不静默截断反馈。
- 反馈内容经过纯文本清理和敏感词处理后再记录。
- 基础限流：单玩家每分钟最多 3 次；游客按其连接身份或游客标识限流。超限不写入反馈记录。
- 反馈失败必须返回明确错误，不得显示提交成功。
- 反馈提交成功只向提交者返回系统提示，不生成普通聊天消息。

## 基础敏感词风控

- 风控只针对普通聊天内容和 `/report` 的内容部分，不针对命令名、命令结构或用户名解析做替换。
- 敏感词命中时采用统一替换文本，不回显原始命中内容。
- 敏感词匹配不得直接把配置文本拼接为未转义正则；词表必须按字面量匹配，避免特殊字符改变匹配语义或造成正则异常。
- 敏感词表来自服务端配置，不由客户端决定，不向客户端暴露完整词表。
- HTML、脚本协议和事件属性等危险内容按纯文本输入处理；客户端渲染不得直接信任服务端原始文本。
- 本阶段不做语义识别、图片/音频审核、机器学习分类、人工审核队列或跨语言高级变形检测。
- 记录风控诊断时不得记录未清理的原始敏感内容。

## 错误与反馈语义

客户端应能区分以下结果：

- 普通文本发送成功。
- 指令不存在。
- 指令参数缺失或过多。
- 当前玩家无权执行指令。
- 目标玩家不存在或不可邀请。
- 邀请已过期、已处理或因队伍已满失败。
- 当前没有队伍/区域上下文。
- 反馈内容为空、过长或触发频率限制。
- 服务端内部处理失败。

错误消息可面向用户显示，但不得包含 token、密码、内部堆栈、数据库连接信息或不必要的其他玩家数据。

## 单一游戏世界约束

- 当前部署中所有在线玩家默认属于同一个游戏世界。
- 全局聊天的可见范围是该世界的所有在线玩家。
- 组队邀请的目标查找范围是该世界中可识别的玩家，不增加房间过滤。
- 区域聊天只按地图格子的 `regionId` 过滤，这是地图空间范围，不是独立游戏房间。
- 任何新增 Socket 房间若仅用于传输优化，不能改变业务上的单一世界语义，也不能成为权限或数据事实源。

## 验收边界

实现完成后至少应验证：

1. `/help` 显示完整且不包含 `/kick`。
2. `/team`、`/region`、`/global` 无参数时分别正确切换频道；带参数时分别切换并将参数作为消息发送到新频道。
3. 普通文本按当前频道发送，`system` 不可由玩家发送；频道消息发送失败时客户端不会显示伪成功。

4. `/invite 唯一用户名` 能创建邀请，找不到用户时返回明确错误。
5. 并发接受/拒绝/过期/满员场景不会重复入队、错误改写邀请状态或产生错误队伍成员。
6. `/accept`、`/reject`、`/leave` 与现有按钮操作使用同一套服务端权威规则。
7. `/kick` 不在帮助、客户端指令解析、服务端指令路由或协议新增项中出现。
8. `/report` 对正式账号和游客均可用，不广播，并写入结构化日志/反馈记录。
9. 反馈空内容、超长内容和频率超限均被拒绝且不写入记录。
10. 敏感词按字面量匹配，聊天和反馈不会回显命中原文。
11. 所有玩家共享同一世界，未引入房间隔离语义。
12. 真实 Socket 集成测试覆盖聊天 ack、频道广播、组队事件和反馈错误路径。

## 不在本文决定的实现选择

以下实现细节留给后续实现计划，不在边界阶段预先规定：

- 指令解析器放在共享层、服务端聊天层还是独立模块。
- 反馈记录使用何种文件格式或已有持久化抽象。
- 客户端是否保留现有组队按钮，以及按钮如何复用指令服务端逻辑。
- 是否使用 Socket.IO 房间作为性能优化；使用时必须遵守单一游戏世界业务约束。
- 聊天历史是否在本里程碑扩展为重连恢复。
